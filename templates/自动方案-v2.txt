# Codex 优化开发提示词：客户需求管理 + 技术方案生成

基于当前已经开发的粗略版本继续优化，**不要推翻现有架构重做**。

本阶段先把两个核心功能做好：

1. 客户技术需求管理
2. 候选技术方案生成

目标是形成：

```text
客户需求
↓
需求结构化
↓
保存需求记录
↓
检索关联历史方案
↓
生成候选技术方案
↓
后续进入审核 / 纠正 / PPT生成
```

---

# 一、客户技术需求

客户需求不能只有固定表单，也不能只有一段AI文本。

采用：

**自由描述 + 固定结构化配置**

两部分组合。

## 1. 自由需求描述

页面顶部提供一个大的需求描述输入框。

销售可以直接输入自己的话，例如：

> 客户需要检测圆柱套筒，要求双工位，节拍1秒两个，检测外观、尺寸和端面缺陷，产品表面可能有少量油，希望自动上料和OK/NG自动下料，设备尽量紧凑。

也可以直接粘贴客户提供的原始需求。

字段建议：

```text
originalRequirement
```

必须永久保存原始文本，不要被AI处理后的内容覆盖。

AI可以根据这段文字帮助自动填写下面的结构化字段，但最终允许人工修改。

---

# 二、固定结构化需求配置

固定配置采用分类形式，不要设计成几十个杂乱字段堆在一起。

第一阶段至少包含：

## 基础信息

```text
客户名称
项目名称
产品名称
产品类型
产品型号
产品尺寸
材质
```

## 产能 / 节拍

```text
目标节拍
每次处理数量
日产能
是否连续生产
```

例如：

```text
目标节拍：1s
每次：2PCS
```

---

## 上料要求

```text
人工上料
振动盘
料仓
提升机
机械手
客户来料线
其他
待确认
```

允许补充文字说明。

---

## 下料要求

```text
OK/NG分料
多级分料
人工收料
自动装箱
接客户产线
其他
```

---

## 检测要求

支持多选，例如：

```text
外观检测
尺寸检测
OCR
缺陷检测
同心度
圆度
平面度
高度
内径
外径
360°线扫
3D检测
其他
```

每个检测项目后续最好可以附：

```text
检测精度
检测范围
备注
```

---

## 产品状态

非常重要，增加：

```text
是否有油
是否有水
是否有粉尘
是否反光
是否透明
是否易划伤
是否易变形
是否有毛刺
是否有锋利边缘
```

采用：

```text
是 / 否 / 未确认
```

不要强制销售一定知道。

---

## 特殊要求

单独提供文本框，例如：

```text
产品不能夹伤
不能接触A面
尖端必须朝指定方向
设备宽度不能超过1500mm
客户指定机器人品牌
必须预留MES接口
```

字段：

```text
specialRequirements
```

---

# 三、AI解析客户需求

提供：

**AI解析需求**

功能。

AI读取：

```text
自由描述
+
当前已有固定配置
```

自动给出结构化建议。

例如原文：

> 客户要求1秒两个，产品有油，需要自动上料。

自动建议：

```text
cycleTime = 1s
parallelQuantity = 2
oil = true
loadingMode = 自动上料
```

但是：

**AI不能直接覆盖人工输入。**

应该展示：

```text
AI识别结果
→ 用户确认
→ 写入正式字段
```

存在不确定内容时：

```text
unknown / 待确认
```

禁止AI自己猜。

---

# 四、客户需求必须数据化管理

每一次客户需求都必须形成独立记录。

建议建立：

```text
Requirement
```

实体。

核心字段至少包括：

```text
id
requirementNo
customerName
projectName
productName
originalRequirement

structuredRequirement

status

createdBy
createdTime
updatedTime
version
```

structuredRequirement 可以使用 JSON 保存详细配置，避免现在过早建立大量数据库字段。

---

# 五、需求管理页面

增加独立：

**技术需求管理**

页面。

列表至少显示：

```text
需求编号
客户
项目
产品
节拍
创建人
创建时间
状态
关联方案数量
```

支持：

```text
查看
编辑
复制需求
生成方案
查看历史方案
删除/归档
```

特别需要：

**复制需求**

因为很多新项目是历史项目的小修改。

---

# 六、需求版本管理

同一个项目后期客户经常会修改要求。

不要直接覆盖旧数据。

例如：

```text
REQ-2026-001 V1
REQ-2026-001 V2
REQ-2026-001 V3
```

至少记录：

```text
修改前
修改后
修改时间
修改人
```

第一阶段可以采用简单版本快照，不需要做复杂Git式版本管理。

---

# 七、需求与历史技术方案关联

Requirement 与历史方案库必须建立关联。

生成技术方案前，根据当前需求检索：

```text
产品类型
产品尺寸
检测项目
节拍
上料方式
工艺
特殊要求
```

寻找历史类似方案。

例如：

```text
当前项目：
圆柱金属套筒
双工位
360°线扫
1s/2PCS
```

系统发现：

```text
历史项目 A：相似度 91%
历史项目 B：相似度 82%
```

这些历史项目作为当前方案生成参考。

不要简单把整个历史PPT全部发给AI。

优先提取：

```text
历史工艺流程
工位结构
使用模块
设备布局
历史方案图片
关键参数
已知问题
```

---

# 八、候选技术方案输出格式

本阶段候选技术方案暂时不要输出大量复杂内容。

**固定只输出以下三部分：**

---

## 1. 历史参考方案

如果检索到合适的历史项目，则显示。

例如：

```text
历史参考方案

项目：XX圆柱套筒检测设备
相似度：91%

参考内容：
- 双工位循环载具
- 360°线扫检测
- V型定位
- OK/NG自动下料
```

最好能够查看：

```text
历史方案图片
历史PPT
项目详情
```

如果没有合适历史项目：

**这一部分直接隐藏。**

不要显示：

```text
暂无历史方案
```

---

# 九、工艺流程

AI基于：

```text
客户需求
+
历史方案
+
标准模块
```

生成工艺流程。

例如：

```text
料仓上料
↓
产品分料
↓
双工位定位
↓
360°旋转线扫
↓
尺寸检测
↓
结果判定
↓
OK / NG分料
```

每一个工位需要结构化保存：

```json
{
  "stationId": "S1",
  "name": "自动上料",
  "description": "料仓+分料机构完成双料同步供料",
  "referenceModule": "",
  "referenceProject": ""
}
```

不要只保存一整段AI文字。

后续PPT和方案图都需要读取这些数据。

---

# 十、结构化方案图提示词

候选方案第三部分是：

**用于AI生成二维技术方案图的结构化提示词。**

注意：

不要只输出普通自然语言Prompt。

需要生成结构化数据。

建议格式：

```json
{
  "drawingType": "industrial_automation_2d_solution",
  "product": {},
  "overallLayout": {},
  "processFlow": [],
  "stations": [],
  "motionRelations": [],
  "keyStructures": [],
  "annotations": [],
  "prohibitedElements": [],
  "referenceImages": []
}
```

---

例如某工位：

```json
{
  "stationId": "S4",
  "name": "360度线扫检测",
  "productPosition": "产品水平放置于双V型滚轮",
  "fixture": "双V型滚轮定位",
  "motion": "伺服电机驱动产品绕自身中心轴旋转",
  "camera": "线扫相机位于产品侧上方",
  "lighting": "条形线光源照射产品外圆",
  "feedingDirection": "左进右出",
  "keyRequirement": [
    "产品旋转中心稳定",
    "无遮挡相机视野",
    "双工位同时检测"
  ]
}
```

然后由专门的 Prompt Builder 把这些结构化数据转换为真正给图片模型的 Prompt。

即：

```text
Solution JSON
↓
Drawing JSON
↓
Prompt Builder
↓
AI图片模型
```

不要：

```text
Solution
↓
让LLM随便写Prompt
↓
画图
```

---

# 十一、二维方案图Prompt必须强调空间关系

这是后续降低AI机械图幻觉的重要基础。

Prompt Builder至少需要明确：

```text
产品在哪里
上料方向
下料方向
机构相对位置
机构数量
运动方向
谁固定
谁移动
谁旋转
相机位置
光源位置
治具位置
禁止出现什么
```

例如不要只描述：

> 使用线扫检测产品。

而要描述：

> 两个圆柱产品水平平行放置在V型滚轮治具上，产品轴线沿X方向，固定线扫相机位于产品正上方偏侧位置，伺服滚轮从产品下方驱动产品绕自身X轴旋转，相机保持固定，产品上方不得存在遮挡机构。

这种数据以后需要从结构化字段生成，而不是靠AI临时发挥。

---

# 十二、候选技术方案的数据关系

建议最终关系：

```text
Requirement
    │
    ├── RequirementVersion
    │
    ├── HistoricalProjectReference
    │
    └── CandidateSolution
              │
              ├── HistoricalReferences
              ├── ProcessFlow
              └── DrawingSpecification
```

CandidateSolution 至少记录：

```text
id
requirementId
version

historicalReferences
processFlow
drawingSpecification

createdTime
createdBy
status
```

为后续加入：

```text
审核
AI纠正
人工修改
PPT生成
```

预留即可，当前阶段不要过度开发。

# 十四、开发要求

先检查当前已经开发的：

```text
Requirement
Solution
历史库
AI调用
PPT模块
```

能复用的全部复用。

不要为了此次需求重新建立一套重复系统。

本轮优先完成：

```text
1. Requirement 数据模型调整
2. 自由描述 + 固定配置UI
3. Requirement CRUD和历史记录
4. AI需求解析
5. Requirement与历史方案关联
6. CandidateSolution数据模型
7. 历史方案检索
8. 工艺流程生成
9. DrawingSpecification生成
10. Prompt Builder
```

暂时不要重点开发复杂：

```text
多Agent
复杂工作流引擎
知识图谱
自动CAD
自动机械设计
```

先保证这一条链路真正可用：

**销售录入一个真实客户需求 → 保存 → 找到历史参考 → 生成合理工艺流程 → 输出稳定的二维方案图结构化Prompt。**

完成后使用至少3组Mock客户需求进行完整端到端测试，并展示最终页面和生成的数据结果。
