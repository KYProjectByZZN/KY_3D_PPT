# Codex 开发提示词：可靠技术方案自动生成模块

你现在需要在我现有的 **PPT 自动生成技术方案软件** 基础上继续优化开发。

当前已经具备 PPT 模板、模块化页面等基础能力。下一阶段重点开发：

**客户技术需求 → 历史方案检索 → 技术方案生成 → 工程审核/纠正 → 技术方案图 → 固定格式 PPT**

参考我提供的技术方案图片风格，最终输出格式需要稳定、统一，不允许 AI 随意改变版式。

## 一、核心目标

解决两个问题：

1. AI直接生成机械/自动化技术方案容易产生工程幻觉，例如结构不合理、机构干涉、节拍错误、工艺顺序错误、参数乱编等。
2. 建立一套可以长期积累、越来越可靠的技术方案生成体系，而不是每次让AI从零设计。

核心原则：

**AI负责理解、检索、选择、组合、分析和纠正；工程数据、参数、规则、结构和正式方案图尽量由历史项目、标准模块和确定性程序提供。**

---

## 二、推荐整体流程

```text
客户需求
↓
需求结构化 Requirement JSON
↓
历史项目检索
↓
标准模块检索
↓
生成候选技术方案
↓
Solution JSON
↓
工程规则审核
↓
发现问题
↓
AI自动纠正
↓
再次审核
↓
低置信度内容人工确认
↓
正式技术方案图
↓
固定PPT模板生成
↓
人工最终审核
↓
优秀方案沉淀回历史库/模块库
```

不要让AI直接：

```text
客户需求 → AI画整机方案图 → PPT
```

---

## 三、需要设计的5个核心模块

### 1. Requirement Engine

负责把客户的：

* Excel
* Word
* PDF
* 人工输入

转换为统一 Requirement JSON。

至少包含：

* 产品信息
* 产品尺寸
* 材料
* 检测项目
* 精度要求
* 节拍
* 产能
* 上下料方式
* 工艺要求
* 客户特殊要求
* 已知限制条件

禁止AI自动编造缺失参数。

缺失内容标记：

```text
unknown
need_confirm
```

---

### 2. Retrieval Engine

建立两类知识库：

#### 历史项目库

不要只保存PPT，而需要拆解：

```text
项目
├ 产品
├ 节拍
├ 工艺流程
├ 整机结构
├ 上料
├ 定位
├ 搬运
├ 检测
├ 压合
├ 旋转
├ 下料
├ 技术参数
├ 已发现风险
└ 最终验证结果
```

支持按照：

* 产品类型
* 尺寸
* 工艺
* 检测方式
* 节拍
* 设备结构

进行相似项目检索。

#### 标准模块库

例如：

```text
上料模块
定位模块
搬运模块
旋转模块
视觉检测模块
线扫模块
压合模块
下料模块
夹具模块
```

每个模块保存：

* moduleId
* 名称
* 使用条件
* 输入参数
* 输出参数
* 适用产品
* 节拍能力
* 尺寸范围
* 结构接口
* 3D模型/图片
* 历史使用项目
* 风险
* 验证状态

优先：

```text
历史方案复用
→ 标准模块组合
→ 参数调整
→ AI新方案
```

---

### 3. Solution Engine

AI不能直接生成最终图片。

首先生成统一：

```text
Solution JSON
```

例如：

```json
{
  "process": [],
  "stations": [],
  "modules": [],
  "cycleTime": {},
  "inspection": [],
  "risks": [],
  "references": []
}
```

每一个工位必须说明：

* 工位编号
* 功能
* 使用模块
* 工作原理
* 产品运动
* 执行机构
* 定位方式
* 检测方式
* 预计节拍
* 参数来源
* 历史参考项目
* 置信度

每个关键结论必须能够追踪来源：

```text
客户要求
历史项目
标准模块
计算结果
人工输入
AI推测
```

如果来源是 AI 推测，必须降低置信度并进入审核。

---

### 4. Validation Engine

这是整个系统最重要的部分。

不能只让LLM自己说“检查一下”。

需要：

**确定性规则 + AI工程审核**

共同完成。

第一阶段优先实现规则：

#### 节拍校验

```text
单工位时间
搬运时间
定位时间
检测时间
设备总CT
并行工位关系
```

判断是否满足客户节拍。

#### 工艺顺序

例如：

```text
上料
→ 定位
→ 检测
→ 组装
→ 压合
→ 检测
→ 下料
```

发现明显顺序错误。

#### 模块兼容性

检查：

* 产品尺寸是否超模块范围
* 负载是否超范围
* 精度是否满足
* 行程是否足够
* 检测方式是否适用

#### 结构风险

检查：

* 产品是否有定位
* 产品是否存在悬空
* 搬运路径
* 相机空间
* 光源空间
* 气缸/电机运动空间
* 旋转机构
* 维护空间
* 安全防护
* 上下料干涉

#### 视觉工艺规则

例如：

圆柱360°线扫：

* 是否有旋转机构
* 是否有稳定定位
* 跳动控制
* 相机与旋转轴关系
* 光源结构
* 转速
* 扫描时间

---

### 5. Rendering Engine

正式技术方案图不要优先使用AI图片。

图片来源优先级：

```text
1 历史项目真实图片
2 标准模块3D图
3 SolidWorks / CAD / STEP自动截图
4 参数化生成图
5 AI概念图
```

AI图片只能用于：

```text
概念设计 / 示意图
```

必须标记：

```text
AI Concept
待工程确认
```

未经人工确认不得作为正式工程结构依据。

---

## 四、方案自动纠正机制

设计三个角色：

```text
Solution Agent
↓
Validation Agent
↓
Correction Agent
```

流程：

```text
生成方案
↓
审核
↓
输出问题列表
↓
修改有问题的局部方案
↓
重新审核
```

不要每次重新生成整套方案。

需要支持：

```text
局部修改
版本对比
撤销
重新审核
人工锁定模块
```

人工锁定后的模块禁止AI随意修改。

---

## 五、增加置信度体系

每个工位/模块显示：

```text
置信度：98%
来源：历史项目直接复用

置信度：90%
来源：标准模块参数调整

置信度：75%
来源：多个历史方案组合

置信度：50%
来源：AI新设计
```

建议分级：

```text
A ≥ 90% 自动通过候选
B 75~89% 建议工程师确认
C <75% 必须人工审核
```

让机械工程师重点审核低置信度内容。

---

## 六、PPT生成要求

参考现有技术方案格式固定生成：

```text
整机布局
工艺流程
S1 上料
S2 检测
S3 自动组装
S4 定位/预压
S5 压合
S6 尺寸检测
S7 3D检测
S8 OK/NG下料
核心夹具
技术参数
检测指标
技术优势
```

每个页面/模块使用固定组件：

```text
标题
设备/机构图片
工作原理
流程箭头
技术标注
关键参数
风险提示
```

AI只提供内容。

**页面坐标、字体、图片区域、边框、颜色、布局由模板程序控制。**

保证同一类型方案每次生成风格稳定。

---

## 七、开发原则

不要一次性重构整个项目。

首先分析现有代码结构，然后给出：

```text
现状
↓
问题
↓
可以复用的代码
↓
需要新增的模块
↓
需要修改的模块
↓
实施顺序
```

优先做最小可用版本 MVP。

推荐开发顺序：

```text
第一阶段
Requirement JSON
+
Solution JSON

第二阶段
历史项目检索
+
标准模块库

第三阶段
工程规则审核

第四阶段
方案纠正

第五阶段
方案图自动生成

第六阶段
与现有PPT生成系统连接
```

不要为了所谓“AI Agent架构”增加大量无必要复杂度。

优先：

**简单、稳定、可维护、可验证。**

---

## 八、三条强制红线

### 红线1

禁止AI创造不存在的机械结构后直接作为正式方案。

### 红线2

关键技术参数必须有明确来源，不允许LLM自行猜测。

### 红线3

AI生成图片不能作为工程真值，正式方案必须优先来源于真实历史结构、标准模块或CAD/3D模型。

---

现在请首先：

1. 阅读并分析当前项目代码。
2. 不要立即大规模修改代码。
3. 梳理当前PPT模块、模板、数据结构和生成流程。
4. 对照以上目标给出现有架构差距。
5. 给出新的目录结构、核心数据模型和模块关系。
6. 给出分阶段开发计划。
7. 优先设计 `Requirement JSON`、`Solution JSON`、`Module`、`ValidationResult` 四个核心数据模型。
8. 方案确认后再逐步编码。
9. 修改过程中尽量复用已有能力，避免重复造轮子。
10. 每完成一个阶段都进行实际测试，确保原有PPT生成功能不被破坏。
